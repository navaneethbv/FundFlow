## Findings

### F1 (P1): background refresh silently reuses selection with newer versions

Locations: `app/transactions/page.tsx:1058`, `components/transactions/TransactionReviewProvider.tsx:54`, `components/transactions/TransactionReviewControls.tsx:118`.
The provider key includes only query entries and page, and selection stores IDs without the version selected by the user.
A background refresh with the same query preserves that selection while replacing `eligibleRows` with new server versions.
Reproduction sequence: select a transaction at version 1, change its amount through a source update, allow the existing auto-refresh to deliver version 2, then click the bulk review button.
The request submits version 2 for the retained selection, so database compare-and-set accepts facts the user did not explicitly reselect.
The provider receives no row signature and contains no changed-row reset logic.
This violates AC-09 and AC-12.
Reset selection when the authoritative ID/version/eligibility set changes, without dropping success feedback, and add an actual refresh interaction test.
Evidence: source trace; the browser sequence was not executed in this review.

### F2 (P1): flag-off rollout breaks takeout and backups before migration

Locations: `lib/user-data.ts:101`, `lib/user-data.ts:196`, `app/api/export/takeout/route.ts:34`, `app/api/cron/backup/route.ts:67`.
The archive registry adds `transaction_review_states` unconditionally.
`collectUserData` queries it even with review disabled and throws on a missing-relation error.
Consequently deploying the application before the new schema is present breaks existing exports and backup collection despite the advertised flag-off compatibility.
An isolated probe with the flag off and a missing-table response reproduced the rejection.
Provide explicit schema-readiness compatibility while preserving archived review records after a UI rollback, or change the rollout contract to require verified schema deployment first.
Do not silently ignore arbitrary database failures or omit already-existing review records whenever the UI flag is disabled.

### F3 (P2): approving the last item on page 2 strands the user on an empty page

Locations: `app/transactions/page.tsx:923`, `app/transactions/page.tsx:1033`, `app/transactions/page.tsx:1145`.
The loader calculates `totalPages` but never redirects or reloads an out-of-range requested page.
With 51 matching entries, reviewing the only entry on page 2 leaves 50 matching entries on page 1, while the refreshed page 2 renders an empty state.
Pagination disappears because `totalPages` is now 1.
An isolated page probe with requested page 2, count 50, and no visible rows reproduced the empty render rather than page recovery.
Implement the last-valid-page navigation required by AC-11 and preserve the remaining URL controls.

### F4 (P2): missing review state is hidden instead of surfacing an integrity error

Locations: `supabase/migrations/20260908040000_transaction_review_state.sql:232`, `app/transactions/page.tsx:823`, `app/transactions/page.tsx:655`.
The view exposes `review_state_missing`, but Needs review excludes missing-state rows through both status and eligibility predicates.
The global count also excludes them and can announce that the user is caught up.
There is no owner-wide missing-state check in the page loader.
In All, the desktop badge is guarded by a truthy `reviewStatus`, so a missing state also suppresses the very badge intended to explain the problem.
This violates the explicit AC-14 integrity-fixture behavior.
Detect incomplete owner state independently of the actionable queue and show an error instead of a reassuring zero count.
Evidence: source trace; no database corruption fixture was created.

### F5 (P2): queue completion, immediate reversal, and keyboard recovery are unfinished

Locations: `lib/ledger-query.ts:210`, `app/transactions/page.tsx:971`, `app/transactions/page.tsx:1036`, `components/transactions/TransactionReviewProvider.tsx:136`.
`hasActiveLedgerFilters` treats `review=needs_review` itself as an active filter, so the queue empty-state branch always displays the filtered-empty message and cannot display its caught-up title.
An isolated page probe reproduced this with no other filters and zero global work.
The global summary can simultaneously say the user is caught up, producing contradictory guidance.
The provider stores `lastResult`, but no component consumes it to render the required immediate Review again action using the returned version.
There is no focus restoration after a reviewed row disappears, and the provider/output unmount when the queue becomes empty.
Complete the success/reversal/focus journey in plan section 4.2 and AC-17, including the final row.

### F6 (P2): the claimed 32 KiB request bound is checked after unbounded buffering

Location: `app/api/transactions/review/route.ts:64`.
A missing or understated Content-Length allows `request.text()` to buffer the entire request before enforcing the limit.
The subsequent check counts JavaScript string length rather than received bytes.
This does not implement the bounded request reading required by plan section 7.1.
Use a byte-counted bounded read and reject oversized input before accumulating the full body.
Evidence: source trace; no oversized network request was sent.
