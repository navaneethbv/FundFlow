## Final findings

### F1 (P2): A valid second authenticator no longer works for restore or account deletion

Location: `lib/step-up.ts:29-31`.
The PR replaces trying verified factors with `factors[0]` whenever no factor ID is supplied.
Both backup restore (`app/api/backup/restore/route.ts:72`) and account deletion (`app/api/account/route.ts:233`) still call without a factor ID.
The application explicitly supports up to ten TOTP factors.
A user entering a valid code from their second enrolled authenticator is now rejected, although the previous implementation accepted it.
An isolated reproduction with two verified factors and a code valid only for the second returns false.
Fix by carrying an explicit selected factor through those forms and routes, or preserving multi-factor verification for callers without a selection.
Add regression coverage for the second-factor path and unknown factor IDs.
This is an introduced regression in the PR.

### F2 (P1): An unavailable factor lookup weakens destructive-action step-up

Location: `lib/step-up.ts:23-26`.
An Auth response containing `data: null` and an error becomes an empty factor list, after which a successful password check returns true.
The isolated reproduction confirmed this decision path using the helper's test password-client branch; production uses a separate password client but makes the same unchecked factor-list decision.
The caller must already pass the normal authenticated-session and AAL checks, and the lookup failure must occur at the later step-up call.
This is not a demonstrated unauthenticated or initial-login MFA bypass.
Fix by rejecting or throwing on factor lookup errors or unusable factor data before choosing any proof method.
This gap predates the PR but remains in the modified helper, whose use expands to MFA unenrollment.
No destructive request was made to a real account to reproduce it.

### F3 (P2): Dashboard recurring amounts and paid status remain inconsistent

Locations: `lib/dashboard.ts:624`, `lib/dashboard.ts:1423`, and `lib/planning-depth.ts:47`.
The isolated reproduction supplies an average amount of 90 and a user correction of 25; Dashboard still returns 90.
The Recurring page uses `userAmount` first.
Dashboard also omits `manual_recurring_items` entirely.
A second reproduction supplies two same-merchant streams and one payment: both streams become paid with the same transaction ID.
The matcher does not consume matches, enforce account or sign identity, or use persisted stream links.
Fix by sharing the recurring occurrence inputs and identity rules, honoring corrected amounts and manual items, and preventing reuse of a payment across distinct occurrences.
These are pre-existing parity gaps explicitly left outstanding in the PR description, not failures of the now-correct dismissal filter.
Month scope also differs: Dashboard derives one status per next date while Recurring expands all occurrences in the selected month.
Transfer categories are excluded from Recurring expense totals but can remain visible occurrences, so mere visibility of a transfer reminder is not by itself a confirmed defect.
