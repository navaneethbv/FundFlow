## Findings in changed behavior

### R1 (P1): The live net-worth endpoint discards manual balances and exclusions

Location: `lib/dashboard.ts:1309`, especially the replacement at line 1311.
The new endpoint is calculated from `allAccounts`, which contains only the `accounts` table, and supplies neither manual balances nor inclusion preferences to `computeNetWorthSnapshot`.
In contrast, `lib/net-worth.ts` includes manual accounts, their `include_in_net_worth` flag, and `dashboard_prefs.accountsPage.excludedNetWorthIds` when writing the historical snapshots.
The new replacement therefore overwrites a correctly composed open-month snapshot with a differently scoped value.
For example, a user with 1,000 in connected cash and an included 500 manual asset gets 1,000 instead of 1,500; an excluded connected account is added back.
The current tests exercise connected-account balances and preserve history, but do not test these inputs.
This is source-confirmed; no manual asset was created in the real account for reproduction.

Fix: load the same permitted balance-sheet inputs and exclusions used by Accounts and snapshot creation before replacing the endpoint.
Keep personal and household scope explicit, retain completed historical observations, and surface query failures instead of substituting incomplete financial totals.
Add regression cases for a manual asset, manual liability, excluded connected account, manual-only user, and unavailable input query.

### R2 (P2): The mobile holdings replacement removes price and quantity

Location: `components/investments/HoldingsTable.tsx:40` through the mobile card body, with the desktop table hidden at line 82.
The mobile card displays name, value, account, weight, and change, but never renders `h.price` or `h.quantity`.
Previously those fields were reachable through horizontal scrolling.
Below the breakpoint they now have no visible equivalent or disclosure control.
The account label also uses `truncate`, so the mask can disappear in the same scenario already corrected in the new Debt cards.
This is confirmed by the rendered branches in source; the real account is in the no-itemized-holdings fallback, so it does not provide a live populated-holdings reproduction.

Fix: include labeled price and quantity in the mobile card and keep account identity readable, or provide an accessible detail disclosure containing those fields.
Verify populated and missing-price/quantity states at 320px and 390px.

## Confirmed remaining audit gaps

### R3 / UI-18 (P1): Dismissed recurring items still appear as overdue on Dashboard

Production reproduction: inspect Dashboard's Recurring card, then Recurring > Manage in the same account and month.
The single T-Mobile stream is marked Not recurring and has a Restore action, while Dashboard still shows it as late.
`lib/dashboard.ts:731` selects active streams without `dismissed_at`, and `buildStreamSummaries` at line 588 cannot exclude dismissed streams.
`lib/recurring-data.ts` supplies dismissal metadata to the dedicated page's occurrence builder.
The PR retains this divergence.
This closes the earlier investigation A for the dismissed-stream case; it does not prove that dismissal explains every differing occurrence.

Fix: honor dismissal before deriving Dashboard reminders and all other recurring summaries.
Audit corrected amounts, manual items, transfer exclusions, linked payment matching, and month scope before claiming full parity between the two implementations.
Test that dismissing a stream removes its reminder and restoring it reintroduces the eligible occurrence.

### R4 / UI-06 follow-up (P2): Dashboard account filters still duplicate masks

Production reproduction: Dashboard's account filter shows a provider name already ending in its mask, followed by the same mask again.
`components/dashboard/DashboardToolbar.tsx:98` still concatenates `account.name` and `account.mask` directly.
`components/dashboard/WealthView.tsx:197` retains the same pattern.
The PR converted other Dashboard labels but missed these two surfaces.

Fix: use `accountDisplayLabel` at these display sites and keep the original account names used for matching unchanged.

### R5 / UI-19 (P2): Admin silently presents a failed sync-job query as an empty panel

Production reproduction: `/admin` reports nonzero total sync jobs and a recent successful sync, but Recent sync jobs is entirely empty.
`app/admin/page.tsx:69` selects `source` from `sync_jobs`; no committed migration creates that column.
The page never checks the query error and renders `recentSyncJobs.data ?? []`.
The empty panel is therefore misleading rather than a genuine no-jobs state.
The page also formats job/audit timestamps as raw ISO strings and maps the schema's `failed` state to warning because its danger test checks `error`.
These are pre-existing issues outside the original 17 findings, discovered while completing the requested all-page review.

Fix: select a real job descriptor such as `job_type`, render query failure and empty states separately, format timestamps, and recognize `failed` as a failure.
Add a schema-aligned query regression and rendered loading/error/empty/status cases.
